# tag-catalog PRD

## 1. 개요

익스텐션이 사용하는 유형 태그(핵심 11종 + 카테고리 14종 + 사용자 커스텀 태그) 목록을
백엔드가 관리하는 API(`GET /api/tags`, `POST /api/tags`)를 제공한다. 프론트엔드의
하드코딩된 `lib/tag-catalog.ts`를 대체하기 위한 기반 작업이며, 실제 프론트 연동은
별도 이슈(FE 담당자)로 분리한다.

## 2. 사용자 스토리

- API 소비자(프론트/향후 다른 클라이언트)로서, 전체 태그 목록을 한 번에 조회해서
  핵심/카테고리 구조로 렌더링하고 싶다.
- API 소비자로서, 사용자가 직접 입력한 새 태그 이름을 등록하고, 이미 있는 태그면
  (대소문자·공백 차이 무관하게) 기존 태그를 재사용하고 싶다.

## 3. 기술 결정

### ADR-1. Tag 엔티티 구조 및 초기 데이터 시딩 방식

**Context** — `GET /api/tags`, `POST /api/tags`를 구현하려면 태그를 저장할 엔티티
구조와, 초기 25개 태그(핵심 11 + 카테고리 14)를 어떻게 DB에 넣을지를 정해야 한다.
현재 프로젝트는 Flyway 없이 `ddl-auto: update` + 단순 단일 테이블 JPA 엔티티(`Problem`
참고) 패턴을 쓰고 있다.

**Decision** — 단일 `Tag` 테이블로 구성한다:
```
Tag(id: Long, name: String, normalizedName: String(unique), category: String)
```
(`createdAt`은 넣지 않는다 — 지은님 API 스펙의 `GET`/`POST` 응답 어디에도 없고, 현재
AC에서 필요로 하는 곳이 없다. 필요해지면 그때 추가한다.)
- `category`는 자유 문자열 컬럼 (`"CORE"`, `"자료구조"`, `"CUSTOM"` 등 값을 그대로 저장)
- `normalizedName`은 `name`을 trim + 소문자 변환한 값으로, 여기에 unique 제약을 걸어
  upsert 매칭과 동시성 문제를 DB 레벨에서 함께 해결한다
- 초기 25개 태그는 `src/main/resources/data.sql`로 시딩한다 (Spring Boot가 앱 기동 시
  자동 실행, Flyway 없이도 표준적으로 동작, 테스트 시 H2에도 동일하게 적용됨)

**Alternatives**
- **category를 Java enum으로 관리 + `ApplicationRunner`로 코드 시딩** — 거부. enum은
  타입 안전성을 주지만 카테고리 추가/변경 시마다 코드 재배포가 필요하고, 이 프로젝트에
  전례 없는 시딩 방식(`ApplicationRunner`)을 새로 들여오게 되어 기존 패턴과의 일관성이
  떨어짐.
- **`Tag`/`TagCategory`를 FK로 분리한 2테이블 구조** — 거부. 카테고리 추가/이름 변경이
  코드 재배포 없이 가능해지는 장점은 있으나, 카테고리 수가 7개로 고정적이고 거의 안
  바뀌는 지금 스코프엔 과설계다. API 응답 매핑에 조인이 추가되고, 테스트 셋업도
  복잡해진다. `Problem` 엔티티가 이미 단순 단일 테이블 패턴이라 일관성도 떨어짐.

**Consequences**
- (+) 가장 단순한 구조. `Problem` 엔티티와 동일한 패턴이라 팀 컨벤션 일관성 높음.
- (+) `data.sql`이 프로덕션/테스트(H2) 양쪽에 동일하게 적용되어 별도 테스트 픽스처
  작성 부담이 적음.
- (+) 카테고리 추가/이름 변경 시 코드 재배포 없이 `data.sql`(또는 향후 실제 데이터)만
  수정하면 됨.
- (−) `category`가 자유 문자열이라, 오타로 잘못된 카테고리 값이 들어가도 컴파일
  타임에 잡히지 않는다 (런타임 검증에 의존).
- (−) 카테고리 목록 자체(어떤 카테고리가 유효한지)를 애플리케이션이 강제하지 않는다 —
  지은님 스펙의 8개 값(`CORE` + 7개 대분류) 외의 값이 실수로 들어갈 수 있음. 필요하면
  Service 레벨에서 화이트리스트 검증을 추가로 고려한다.

## 4. Out of Scope

- 프론트엔드 연동 (`lib/tag-catalog.ts` 교체, `TagPicker`/`TagFilterPanel` 수정) — 별도 이슈
- 태그 삭제/수정 API
- 관리자 태그 관리 화면
- 태그 이름 길이 제한 등 추가 검증
- 페이지네이션
- Flyway 도입 (프로젝트 전체 마이그레이션 전략은 이 이슈 범위 밖)
- 카테고리 값 화이트리스트 검증 (ADR-1의 알려진 제약, 필요 시 후속 이슈)
- 번역/동의어 매칭 (예: "트리" 입력 후 "tree"를 입력해도 같은 태그로 인식) — 정규화는
  trim + 대소문자 무시까지만 처리하며, 언어가 다른 동의어는 별개의 커스텀 태그로
  생성된다. 커스텀 태그가 누적되면 사실상 중복 태그가 카탈로그에 쌓일 수 있는
  알려진 제약이며, 필요 시 후속 이슈(예: 관리자 태그 병합 기능)에서 다룬다.
