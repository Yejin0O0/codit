# tag-edit-delete 요구사항

## 개요

`tag-catalog`(이슈 #40)가 조회(`GET /api/tags`)·등록(`POST /api/tags`)만 다루고
"태그 삭제/수정 API"를 명시적으로 Out of Scope로 남겼던 것의 후속 기능이다. 이번
기능은 서로 다른 리소스를 다루는 두 가지 백엔드 API를 함께 다룬다.

1. **태그 카탈로그 CRUD** — 사용자가 만든 커스텀 태그(`category: "CUSTOM"`) 자체의
   이름을 수정하거나 카탈로그에서 삭제한다. (`Tag` 리소스)
2. **기록에 연결된 태그 수정** — 특정 기록(`Attempt`)에 붙어 있는 태그 목록을
   교체한다. (`Attempt` 리소스, `attempt_tag` 조인 테이블)

두 API 모두 이번 이슈(태그 담당)에서 백엔드까지 구현한다. **프론트엔드 연동은 별도
FE 이슈로 분리한다** — `tag-catalog`의 관례를 따름. 현재 담당자가 FE 화면(어느
진입점에서 트리거되는지)을 정하지 않은 상태이므로, 이번 이슈는 API 계약과 동작
규칙 확정에 집중한다.

## 사용자 시나리오

**시나리오 A — 커스텀 태그 이름 정상 수정**
Given 사용자가 만든 커스텀 태그 `{ id: 26, name: "이분그래프", category: "CUSTOM" }`가 있다
When 사용자가 이름을 `"이분 그래프"`로 수정 요청한다
Then 서버는 이름을 바꾸고 `200 OK`로 갱신된 태그를 반환한다

**시나리오 B — 이름 수정이 기존 태그와 충돌**
Given 커스텀 태그 `"이분그래프"`(id 26)와 CORE 태그 `"DFS"`(id 6)가 있다
When 사용자가 태그 26의 이름을 `"dfs"`로 수정 요청한다 (trim + 대소문자 무시 시 6과 동일)
Then 서버는 수정하지 않고 `409 TAG_NAME_CONFLICT`를 반환한다

**시나리오 C — CORE/카테고리 태그는 수정 대상이 아님**
Given `category: "CORE"`인 태그(id 6, `"DFS"`)가 있다
When 사용자가 태그 6의 수정/삭제를 요청한다
Then 서버는 `403 TAG_NOT_EDITABLE`을 반환한다 (CORE/카테고리 태그는 `GET /api/tags`로
공개된 정보라 존재 자체는 숨기지 않음)

**시나리오 D — 기록에 안 쓰인 커스텀 태그 삭제**
Given 커스텀 태그 26이 어떤 `Attempt`에도 연결돼 있지 않다
When 사용자가 태그 26 삭제를 요청한다
Then 서버는 태그를 삭제하고 `204 No Content`를 반환한다

**시나리오 E — 기록에 쓰인 커스텀 태그 삭제 시도**
Given 커스텀 태그 26이 기록 3개에 연결돼 있다
When 사용자가 태그 26 삭제를 요청한다
Then 서버는 삭제하지 않고 `409 TAG_IN_USE`를 반환한다

**시나리오 F — 존재하지 않는 태그 id**
Given id 999인 태그가 없다
When 사용자가 태그 999의 수정/삭제를 요청한다
Then 서버는 `404 TAG_NOT_FOUND`를 반환한다

**시나리오 G — 기록의 태그를 정상적으로 교체**
Given 사용자 본인의 기록에 태그 `[4, 6]`이 연결돼 있다
When 사용자가 태그 목록을 `[4, 6, 26]`로 수정 요청한다 (전체 교체 방식)
Then 서버는 연결을 갱신하고 `200 OK`를 반환한다

**시나리오 H — 기록에서 마지막 태그 제거 시도**
Given 사용자 본인의 기록에 태그 `[6]` 하나만 남아있다
When 사용자가 태그 목록을 `[]`(빈 배열)로 수정 요청한다
Then 서버는 거부하고 `409 MIN_TAG_REQUIRED`를 반환한다

**시나리오 I — 다른 사용자의 기록 수정 시도**
Given 기록(attempt id 10)이 사용자 A 소유다
When 사용자 B가 attempt 10의 태그 수정을 요청한다
Then 서버는 `404 ATTEMPT_NOT_FOUND`를 반환한다 (비공개 리소스라 존재 여부를 숨김.
attempt id 자체가 없는 경우와 동일하게 취급)

## 경계 조건 및 엣지 케이스

- **CUSTOM 태그만 수정/삭제 가능**: `CORE`/카테고리 태그(시딩 데이터, 전역 공용)는
  수정도 삭제도 불가. 시도 시 `403 TAG_NOT_EDITABLE`.
- **삭제 시 사용 중 여부 확인**: 커스텀 태그가 하나 이상의 `Attempt`에 연결돼 있으면
  삭제 차단(`409 TAG_IN_USE`). 사용자가 먼저 각 기록에서 태그를 뗀 후 삭제해야 한다.
  (병합/cascade는 하지 않는다 — Out of Scope)
- **이름 수정 시 중복 검사**: 새 이름이 trim + 대소문자 무시 기준으로 다른 태그
  (`CORE`/카테고리/다른 `CUSTOM`)와 같아지면 차단(`409 TAG_NAME_CONFLICT`). 자동
  병합은 하지 않는다.
- **빈 이름**: 수정 요청의 `name`이 없거나 공백만 있으면 기존 `POST /api/tags`와
  동일하게 `400 INVALID_REQUEST`.
- **기록의 최소 태그 수**: `attempt-recording`에서 확정된 "기록당 태그 최소 1개
  필수" 불변 조건을 그대로 유지한다. 태그 교체 요청 결과 태그가 0개가 되면
  `409 MIN_TAG_REQUIRED`.
- **기록 소유권 검증**: 기록의 태그를 수정할 수 있는 사람은 그 `Attempt.userId`
  본인뿐이다. 다른 사용자의 기록이거나 존재하지 않는 attempt id는 구분 없이
  `404 ATTEMPT_NOT_FOUND`.
- **존재하지 않는 태그/기록 id**: 각각 `404 TAG_NOT_FOUND` / `404 ATTEMPT_NOT_FOUND`.

## 에러 처리 방식

기존 `InvalidRequestException` + `GlobalExceptionHandler` 패턴을 재사용한다. 신규
에러 코드:

| 코드 | Status | 상황 |
|---|---|---|
| `INVALID_REQUEST` | 400 | 태그 이름이 없거나 빈 값/공백 (기존 코드 재사용) |
| `TAG_NOT_FOUND` | 404 | 수정/삭제하려는 태그 id가 존재하지 않음 |
| `TAG_NOT_EDITABLE` | 403 | `CORE`/카테고리 태그를 수정/삭제하려 함 |
| `TAG_NAME_CONFLICT` | 409 | 수정하려는 이름이 이미 다른 태그와 겹침 |
| `TAG_IN_USE` | 409 | 삭제하려는 태그가 하나 이상의 기록에 연결돼 있음 |
| `ATTEMPT_NOT_FOUND` | 404 | 기록 id가 없거나, 본인 소유가 아님 (구분하지 않음) |
| `MIN_TAG_REQUIRED` | 409 | 기록의 태그를 0개로 만들려는 요청 |

## Out of Scope (초안)

- 프론트엔드 연동 (UI 진입점, 컴포넌트 수정) — 별도 FE 이슈
- `CORE`/카테고리 태그 수정/삭제, 관리자 태그 관리 화면
- 태그 병합(merge) 기능 — 이름 중복 시 자동 병합하지 않고 차단만 한다. 후속 이슈로
  남김 (`tag-catalog` PRD가 이미 예고한 "관리자 태그 병합 기능")
- 태그 이름 길이 제한 등 추가 검증 (필요 시 후속 이슈)
- 페이지네이션
- 소프트 삭제 (완전 삭제만 지원)
- "기록당 태그 최소 1개" 정책 자체의 변경 (`attempt-recording`에서 확정된 기존
  불변 조건을 그대로 따름)

## 용어 정의

| 용어 | 의미 |
|---|---|
| 커스텀 태그 | 사용자가 `POST /api/tags`로 생성한 태그. `category: "CUSTOM"`. 이번 기능의
수정/삭제 대상 |
| 태그 카탈로그 CRUD | 커스텀 태그 자체의 이름 수정(`PUT`) 및 삭제(`DELETE`). `Tag`
엔티티에 대한 조작 |
| 기록 태그 수정 | 특정 `Attempt`에 연결된 태그 목록을 교체하는 조작.
`attempt_tag` 조인 테이블에 대한 조작이며 `Tag` 엔티티 자체는 건드리지 않음 |
| 사용 중(in use) | 커스텀 태그가 하나 이상의 `Attempt`와 `attempt_tag`로 연결돼
있는 상태. 삭제 차단 조건 |
| 병합(merge) | 이름이 겹치는 두 태그를 하나로 합치고 관련 기록을 재연결하는 동작.
이번 기능에서는 지원하지 않음 (Out of Scope) |
