# tag-catalog 요구사항

## 개요

익스텐션이 사용하는 유형 태그(핵심 11종 + 카테고리 14종 + 사용자 커스텀 태그) 목록을
백엔드가 관리하도록 하는 API. 프론트엔드의 하드코딩된 `lib/tag-catalog.ts`를 대체하기
위한 조회/등록 API를 제공한다. **이 이슈는 백엔드 API 구현까지만 다루며, 프론트엔드가
이 API를 실제로 호출하도록 연동하는 작업은 별도 이슈(프론트 담당자)로 분리한다** —
`docs/features/problem-identification/issues.md`의 FE/BE 역할 분리 관례를 따름.

## 사용자 시나리오

**시나리오 1 — 태그 전체 목록 조회**
`GET /api/tags` 호출 시, 핵심 태그 11개(`category: "CORE"`) + 카테고리별 태그 14개
(`category`: 대분류명) 총 25개를 배열로 반환한다.

**시나리오 2 — 새 커스텀 태그 등록**
`POST /api/tags`에 `{ "name": "이분 그래프" }`처럼 기존에 없는 이름을 보내면, 새
`Tag`(`category: "CUSTOM"`)를 생성하고 `201 Created`로 반환한다.

**시나리오 3 — 기존 태그 재사용 (대소문자/공백 무관 매칭)**
`POST /api/tags`에 이미 존재하는 태그와 대소문자/앞뒤 공백만 다른 이름(예: 기존
CORE 태그 `"DFS"`에 대해 `"dfs"`, `" DFS "`)을 보내면, 새로 생성하지 않고 기존 태그를
`200 OK`로 반환한다. CORE/카테고리 태그와 커스텀 태그 사이에도 동일하게 적용된다.

## 경계 조건 및 엣지 케이스

- **빈 이름**: `POST /api/tags`에 빈 문자열이나 공백만 있는 `name`을 보내면
  `400 Bad Request`로 거부한다.
- **동시 생성 (동시성)**: 두 요청이 거의 동시에 같은 이름으로 처음 등록을 시도하면,
  DB에 `name`(정규화 기준) unique 제약을 두어 하나만 성공시키고, 실패한 쪽은 재조회해
  기존 태그를 반환한다. 중복 태그가 생기지 않는다.
- **매칭 기준**: 이름 비교는 trim + 대소문자 무시로 정규화한 뒤 수행한다. 프론트엔드
  `tag-input.ts`의 `resolveCustomTagInput` 정규화 로직과 동일한 기준이며, 프론트를
  거치지 않고 API를 직접 호출해도 같은 결과가 보장되어야 한다.
- **카테고리 값**: `POST /api/tags`로 생성되는 태그의 `category`는 항상 서버가
  `"CUSTOM"`으로 고정 지정한다. 요청 스키마에 `category` 필드는 없다.

## 에러 처리 방식

기존 `InvalidRequestException` + `GlobalExceptionHandler` 패턴(문제 식별 API에서
이미 사용 중)을 그대로 재사용한다. 새 에러 코드 체계를 만들지 않는다.

- `400 Bad Request`: `{ "code": "INVALID_REQUEST", "message": "..." }` — `name` 누락/빈 값

## Out of Scope (초안)

- 프론트엔드 연동 (`lib/tag-catalog.ts` 교체, `TagPicker`/`TagFilterPanel` 수정) — 별도 이슈
- 태그 삭제/수정 API
- 관리자 태그 관리 화면
- 태그 이름 길이 제한 등 추가 검증 (필요 시 후속 이슈)
- 페이지네이션 (전체 태그 수가 적어 불필요, 향후 커스텀 태그가 많아지면 재검토)

## 용어 정의

| 용어 | 의미 |
|---|---|
| CORE 태그 | 핵심 태그 11종. 카테고리 구분 없이 항상 플랫 노출 |
| 카테고리 태그 | "더보기" 클릭 시 노출되는 14종. `category` 값이 대분류명(자료구조/그래프 등) |
| 커스텀 태그 | 사용자가 직접 입력해 `POST /api/tags`로 생성한 태그. `category: "CUSTOM"` |
| Upsert | 이미 있으면 기존 것을 반환하고, 없으면 새로 생성하는 동작 (`/api/problems`와 동일 패턴) |
