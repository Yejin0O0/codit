# My PRD

`spec-fixed.md`를 입력으로 받아 코드베이스 탐색 → 아키텍처 비교 → ADR → `prd.md` 저장까지 진행하는 스킬.

```
spec-fixed.md (확정된 요구사항)
    ↓ 코드베이스 탐색
    ↓ 아키텍처 3안 비교 (7가지 고정 기준)
    ↓ [GATE] 사용자 선택
    ↓ ADR 작성
    ↓ Out of Scope 확정
    ↓ [GATE] 사용자 확정
prd.md (단일 기준 문서)
```

---

## 시작 전: 입력 확인

1. **feature 이름** — 사용자 메시지에서 추출하거나, 없으면 질문한다.
2. **spec-fixed.md 확인** — `docs/features/{name}/spec-fixed.md`를 읽는다.
   - 없으면: "spec-fixed.md가 없습니다. 요구사항 인터뷰(/feature-planner)를 먼저 진행해주세요." 안내 후 중단.
3. **spec 품질 점검** — 아키텍처 3안을 구체적으로 제안하려면 spec에 아래 항목이 있어야 한다.
   - 데이터 구조 (어떤 필드/타입인가)
   - 핵심 동작 (입력·저장·삭제 등 주요 흐름)
   - 경계 조건 (유효성 규칙, 제한값)

   하나라도 빠져 있으면 진행 전에 사용자에게 알린다.
   예: "spec-fixed.md에 데이터 구조가 명시되지 않아 아키텍처 안이 추상적으로 나올 수 있습니다. 보완 후 진행하거나, 이대로 진행할지 선택해주세요."
4. **prd.md 확인** — 이미 있으면 사용자에게 덮어쓸지 확인한다.

---

## 1단계: PRD 뼈대 생성

기술 결정 섹션은 TODO로 비워두고 먼저 `docs/features/{name}/prd.md`를 생성한다.

```markdown
# {기능명} PRD

## 1. 개요
## 2. 사용자 스토리
## 3. 기술 결정 (TODO)
## 4. Out of Scope
## 5. 용어 정의
```

개요와 사용자 스토리는 spec-fixed.md에서 그대로 가져온다.

---

## 2단계: 코드베이스 탐색

아키텍처 안을 제안하기 전에 코드베이스를 반드시 먼저 읽는다.
탐색 없이 안을 제안하면 기존 패턴과 동떨어진 제안이 나온다.

탐색 대상:
- 관련 컴포넌트, Context, API 파일
- 기존 데이터 구조 (타입 정의)
- 유사한 기능이 이미 있다면 그 구현 방식

---

## 3단계: 아키텍처 3안 비교

코드베이스 탐색을 마친 뒤 **구체적인 코드 예시**를 포함한 3가지 구현 안을 제안하고, 아래 **7가지 고정 기준**으로 비교 표를 만든다.

| # | 기준 | 설명 |
|---|------|------|
| 1 | 데이터 구조 | 어떤 형태로 데이터를 저장/표현하는가 |
| 2 | API 레이어 변경지점 | 기존 API에서 무엇이 바뀌는가 |
| 3 | 상태관리 변경지점 | Context/Store에서 무엇이 추가되는가 |
| 4 | 핵심 동작 | 이 기능의 가장 중요한 동작이 어떻게 구현되는가 |
| 5 | 컴포넌트 구조 | 어떤 컴포넌트가 추가/수정되는가 |
| 6 | 기존 패턴과의 일관성 | 코드베이스의 기존 관습과 얼마나 맞는가 |
| 7 | 테스트 용이성 | 단위 테스트, E2E 테스트 작성이 쉬운가 |

비교 표 뒤에 **추천 안과 이유**를 반드시 제시한다.
이유는 두 가지만: 가장 강한 이유 2개를 골라 짧게 쓴다.
사용자가 "추천이 뭐야?"라고 물으면 이미 제시한 것을 반복하지 말고 이유를 더 구체적으로 설명한다.

### [GATE] 안 선택 대기

비교 표와 추천을 제시한 뒤 **사용자가 안을 선택할 때까지 기다린다.**
선택 전에 ADR 작성이나 다음 단계로 넘어가지 않는다.

---

## 4단계: ADR 작성

선택한 안을 PRD "기술 결정" 섹션에 ADR 형식으로 작성한다.

```markdown
### ADR-{N}. {결정 제목}

**Context**
이 결정이 필요한 맥락. 무엇을 풀고 있는가.
맥락이 길면 여러 줄로 쓴다 — 인라인 dash(—)로 이어붙이지 않는다.

**Decision**
무엇을 선택했는가.

**Alternatives**

- **{거부한 안}**: 거부 이유.
  (이유 없는 거부 금지. "단순히 복잡해서"는 이유가 아니다 — 무엇이 복잡하고 왜 그게 문제인지 써야 한다.)

**Consequences**

- (+) 장점
- (-) 단점
```

Consequences는 `(+)` / `(-)` 기호를 사용한다.
단점 없는 ADR은 신뢰하기 어렵다 — 반드시 `(-)`를 하나 이상 포함한다.

주요 결정마다 별도 ADR을 작성한다. 하나의 기능에 데이터 구조 결정과 상태 관리 결정이 별개라면 ADR-1, ADR-2로 나눈다.

---

## 5단계: Out of Scope 확정

"하지 않을 것"을 구체적으로 나열한다.
spec-fixed.md의 Out of Scope 초안을 시작점으로 쓰되, 기술 결정 과정에서 새로 드러난 제외 항목을 추가한다.

Out of Scope가 명확할수록 이후 이슈 분해 때 범위가 흔들리지 않는다.

### [GATE] Out of Scope 확정 대기

목록을 사용자에게 제시하고 **"확정"** 을 받을 때까지 기다린다.
확정 후 prd.md를 저장한다.

---

## 산출물: prd.md

`docs/features/{name}/prd.md` 최종 구조:

```markdown
# {기능명} PRD

## 1. 개요
## 2. 사용자 스토리
## 3. 기술 결정
  ### ADR-1. ...
  ### ADR-2. ... (필요 시)
## 4. Out of Scope
## 5. 용어 정의
```

## 게이트 요약

| 지점 | 확인 내용 | 다음 단계 진입 조건 |
|------|----------|-------------------|
| 3단계 후 | 아키텍처 3안 비교 | 사용자가 안 번호로 선택 |
| 5단계 후 | Out of Scope 목록 | 사용자 "확정" 명시 |

게이트에서 사용자의 명시적 확인 없이는 절대 다음 단계로 넘어가지 않는다.
