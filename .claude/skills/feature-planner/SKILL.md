# Feature Planner

아이디어를 실행 가능한 이슈 단위로 변환하는 3단계 파이프라인.

```
spec-original.md (초기 아이디어)
    ↓ 단계 1 — 요구사항 인터뷰
spec-fixed.md (확정된 요구사항)
    ↓ 단계 2 — PRD 작성 + 기술 결정(ADR)
prd.md (단일 기준 문서)
    ↓ 단계 3 — 이슈 분해
issues.md + GitHub Issues (실행 가능한 작업 단위)
```

---

## 시작 전: 진입 지점 파악

스킬 실행 시 feature 이름과 현재 단계를 먼저 확인한다.

1. **feature 이름** 확인 — 사용자 메시지에서 추출하거나, 없으면 질문한다.
2. **기존 파일 확인** — `docs/features/{name}/` 디렉터리를 탐색해 진입 지점을 결정한다:
   - `spec-original.md` 없음 → 사용자에게 초기 아이디어 작성을 안내한 뒤 단계 1 진행
   - `spec-original.md` 있고 `spec-fixed.md` 없음 → 단계 1
   - `spec-fixed.md` 있고 `prd.md` 없음 → 단계 2
   - `prd.md` 있고 `issues.md` 없음 → 단계 3
   - 모두 있음 → 사용자에게 어느 단계를 다시 진행할지 질문

모든 파일은 `docs/features/{name}/` 아래에 저장한다.

---

## 단계 1: 요구사항 인터뷰

### 목적
초기 기능 정의서의 모호성을 제거하고, 엣지 케이스와 결정 사항을 확정한다.

### 인터뷰 방식
**한 번에 하나의 질문만 한다.** 추천 방식이 있다면 이유와 함께 제시한다.

아래 8가지 영역을 순서대로 다룬다 (답변이 이미 spec-original.md에 있으면 건너뛴다):

1. 이 기능의 primary user는 누구인가?
2. 최소 동작 시나리오 3개는? (가장 기본적인 사용 흐름)
3. 데이터 저장 방식 — 기존 구조와의 관계는?
4. 경계 조건 — 최대값, 빈 값, 중복, 동시성은?
5. 에러 처리 — 실패 시 사용자에게 어떻게 표시하는가?
6. 기존 UI 패턴과의 일관성 — 어떤 컴포넌트를 재사용할 수 있는가?
7. 성능 제약 — 허용 응답 시간, 데이터 크기 제한은?
8. 향후 확장 가능성 — 이 결정이 다음 feature에 영향을 주는가?

### Ubiquitous Language 정의
인터뷰 과정에서 등장한 핵심 용어를 고정한다. 코드·문서·대화에서 같은 단어로 같은 것을 가리켜야 한다. spec-fixed.md의 "용어 정의" 섹션에 명시한다.

### 산출물: spec-fixed.md

인터뷰 완료 후 `docs/features/{name}/spec-fixed.md`를 작성한다. 구조:

```markdown
# {기능명} 요구사항

## 개요
## 사용자 시나리오
## 경계 조건 및 엣지 케이스
## 에러 처리 방식
## Out of Scope (초안)
## 용어 정의
```

### [GATE] 단계 1 승인

```
사용자가 spec-fixed.md를 읽고 확정할 때까지 대기한다.
수정 요청이 있으면 반영 후 다시 대기한다.
확정 후에만 단계 2로 진행한다.
```

## 단계 2: PRD 작성 + 기술 결정(ADR)

### 목적
요구사항·디자인·기술 결정·범위를 하나의 문서로 통합해 "이 기능에 대해 궁금하면 여기만 보면 된다"는 단일 기준점을 만든다.

---

### 2-1. PRD 뼈대 생성

기술 결정 섹션은 TODO로 비워두고 먼저 뼈대를 작성한다.

```markdown
# {기능명} PRD

## 1. 개요
## 2. 사용자 스토리
## 3. 기술 결정 (TODO — 2-2, 2-3 완료 후 채움)
## 4. Out of Scope
## 5. 용어 정의
```

---

### 2-2. 아키텍처 3안 제안 & 비교

코드베이스를 탐색한 뒤 최소 3가지 구현 안을 제안하고, 아래 **7가지 고정 기준**으로 비교 표를 작성한다:

| # | 기준 | 설명 |
|---|------|------|
| 1 | 데이터 구조 | 어떤 형태로 데이터를 저장/표현하는가 |
| 2 | API 레이어 변경지점 | 기존 API에서 무엇이 바뀌는가 |
| 3 | 상태관리 변경지점 | Context/Store에서 무엇이 추가되는가 |
| 4 | 핵심 동작 | 이 기능의 가장 중요한 동작이 어떻게 구현되는가 |
| 5 | 컴포넌트 구조 | 어떤 컴포넌트가 추가/수정되는가 |
| 6 | 기존 패턴과의 일관성 | 코드베이스의 기존 관습과 얼마나 맞는가 |
| 7 | 테스트 용이성 | 단위 테스트, E2E 테스트 작성이 쉬운가 |

### [GATE] 단계 2-2 승인

```
비교 표를 사용자에게 제시한다.
사용자가 3안 중 하나를 선택할 때까지 대기한다.
선택 후에만 2-3으로 진행한다.
```

---

### 2-3. ADR 작성

선택한 안을 PRD "기술 결정" 섹션에 ADR 4요소로 작성한다.

```markdown
### ADR-{N}. {결정 제목}

**Context** — 이 결정이 필요한 맥락. 무엇을 풀고 있는가.

**Decision** — 무엇을 선택했는가.

**Alternatives** — 거부한 안과 각각의 거부 이유. (이유 없는 거부 금지)

**Consequences** — 트레이드오프. 장점뿐 아니라 단점도 반드시 명시한다.
```

주요 결정마다 별도 ADR을 작성한다 (데이터 구조, 상태 관리, UX 방식 등).

---

### 2-4. Out of Scope 작성

"하지 않을 것"을 구체적으로 나열한다. 명시하지 않으면 범위 초과 구현이 발생한다.

예시 형식:
```markdown
## 4. Out of Scope

- {기능명} 기반 필터링 / 검색
- 자동완성 (기존 데이터 제안)
- 전용 관리 화면
- 순서 변경 (드래그 앤 드롭)
```

### [GATE] 단계 2-4 승인

```
Out of Scope 목록을 사용자에게 제시한다.
사용자가 읽고 확정할 때까지 대기한다.
확정 후 prd.md를 저장하고 단계 3으로 진행한다.
```

### 산출물: prd.md

`docs/features/{name}/prd.md`에 완성된 PRD를 저장한다.

## 단계 3: 이슈 분해

### 목적
PRD를 실행 가능한 작업 단위(GitHub Issues)로 변환한다. 각 이슈는 독립적으로 TDD 사이클을 돌릴 수 있어야 한다.

### 수직 슬라이싱 원칙 (필수)

> "이 이슈만 완료하면 사용자에게 보여줄 수 있는 동작이 있는가?"

- **Yes** → 수직 슬라이스. TDD 사이클을 돌릴 수 있다.
- **No** → 다른 이슈와 합치거나 다시 나눈다.

**수평 슬라이싱 금지.** 레이어별(API → Context → UI) 분리는 마지막 이슈까지 완료해야 동작이 나오므로 TDD 사이클을 이슈 단위로 돌릴 수 없다.

수평 슬라이싱 신호:
- 이슈 완료 후 사용자가 새롭게 할 수 있는 것이 없음
- Given/When/Then 시나리오가 기존 동작을 그대로 기술 (회귀 테스트 수준)
- 이슈 설명이 특정 기술 레이어만 언급 ("타입 추가", "API 수정")

### 이슈 크기
반나절~하루 안에 TDD 사이클(Red→Green→Refactor) 완료 가능한 단위.

### 의존성 순서
앞 이슈의 결과가 다음 이슈의 입력이 되도록 배치한다. 역방향 개발 금지.

### 이슈 형식

각 이슈를 아래 구조로 작성한다:

```markdown
## Issue N: [기능명] 이슈 제목

### 설명
무엇을 구현하는가. 왜 이 단계에서 하는가. 신규 파일이 있으면 나열한다.

### 완료 조건 (Acceptance Criteria)
- [ ] AC 항목 1
- [ ] AC 항목 2

### 시나리오

**시나리오 A — 시나리오 이름**

**Given** 사전 조건  
**When** 사용자 행동  
**Then** 기대 결과
```

### [GATE] 단계 3 승인

```
이슈 목록을 사용자에게 제시한다.
수직 슬라이스 기준 충족 여부를 사용자가 확인할 때까지 대기한다.
확정 후 issues.md 저장 및 GitHub 등록으로 진행한다.
```

### GitHub 등록

```bash
gh issue create \
  --title "[{기능명}] 이슈 제목" \
  --body "$(cat <<'EOF'
### 설명
...

### 완료 조건
- [ ] ...

### 시나리오
**Given** ...
**When** ...
**Then** ...

의존: #{앞 이슈 번호}
EOF
)"
```

등록 후 프로젝트 칸반 보드 Todo 컬럼에 배치한다:

```bash
gh project item-add <PROJECT_NUMBER> --owner <OWNER> --url <ISSUE_URL>
```

### 산출물

- `docs/features/{name}/issues.md`
- GitHub Issues (각 이슈에 AC 포함)

## 승인 게이트 요약

| 지점 | 확인 내용 | 다음 단계 진입 조건 |
|------|----------|-------------------|
| 단계 1 후 | spec-fixed.md — 모호성 제거, 용어 확정 | 사용자 "확정" 명시 |
| 단계 2-2 후 | 3가지 안 비교 — 사용자가 안을 선택 | 사용자가 번호로 선택 |
| 단계 2-4 후 | Out of Scope — 범위 확정 | 사용자 "확정" 명시 |
| 단계 3 후 | 이슈 목록 — 수직 슬라이스, AC 구체성, 의존성 순서 | 사용자 "확정" 명시 |

게이트에서 사용자의 명시적 확인 없이는 다음 단계로 진행하지 않는다.
